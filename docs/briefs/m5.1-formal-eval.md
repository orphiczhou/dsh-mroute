## 0. 用户原始要求（不可曲解）

> 「一个进行模型正式评测，评测后结果**按照我们的能力配置参数分级**做报告给我看，**需我统一才能更新**。」

拆成三条硬约束：

1. **要正式评测**：不是 MVP 的 6 题，要够统计用（per-dimension n 足够算 Wilson 下界）。
2. **按我们的能力配置参数分级**：报告要用**我们自己的六维能力档位量表**（`excellent | good | fair | none`，见 §4）给每个模型逐维建议档位，而不是只说「正确率 83%」。
3. **必须由用户确认后才能更新配置**：本轮**绝不写** `model_ratings` / `channels[]` / 不实现「确认采纳」按钮。评测过程写 `model_eval` / `eval_status`（这是**测量记录**，不是能力配置）是允许且必须的。

## 2. 要交付什么

### 2.1 新题集 `plugin-mroute/lib/eval/suite-formal.mjs`

- `SUITE_VERSION = 'formal/1'`，导出与 lite 同形状的 `TASKS`（元素字段沿用 lite：`id`、`dimension`、`prompt`、`maxTokens`、`grade(text)`、`fixture_pass`、`fixture_fail`、可选 `sentinel: true`、可选 `tools` 声明）。
- **题量**（每个 graded 维都要够算 per-dim Wilson，别少写）：

  | 维度 | 题数 | 是否 graded |
  |---|---|---|
  | `coding` | **12** | graded |
  | `tools` | **12** | graded |
  | `long_context` | **12** | graded |
  | `orchestration` | **8** | graded |
  | `world_knowledge` | **2** | sentinel（不计 composite） |
  | `vision` | 1 | 恒 `null`、零调用 |

  合计调用数/模型 = 12+12+12+8+2 = **46**；四个候选模型共 **184 次**（日预算 200，留 16 次余量）。
- **题必须确定性可判**：`grade(text)` 只看文本里的可验证特征（精确字符串/正则/JSON 可解析且字段合法/数值正确），**不许**用 LLM 当裁判。
- **每道题必须有 `fixture_pass` / `fixture_fail`**：`sentinelCheck` 会用它自证判分器（零模型调用）。若某题写不出合格 fixture，就别用那题。
- **成本控制**：单题 `maxTokens` ≤ 512（coding 可 1024），prompt 尽量短；tools 题用 `tools` 声明（`[get_weather]` 这类），不要造复杂 schema。
- 题面**不得**依赖外部网络或长上下文文件；long_context 题用「长文本内嵌唯一 token，要求同时回答两处」这类可自动判的形式（长文本可以内嵌在 prompt 里，控制在 ~1500 tokens 内）。

### 2.2 工具侧接入（最小改动）

- `lib/tool-eval-run.mjs` 增入参 `suite`：`{ type: 'string', enum: ['lite','formal'] }`，缺省 `'lite'`（**向后兼容，现有 dry_run 行为不变**）；`formal` 时用 `suite-formal.mjs`。
- **宿主工具 schema 只接受单一 type 字符串**（禁 `type: [...]`）——这是踩过的坑（M4.8 三工具全消失），照抄现有写法。
- 其它入参语义不变：`dry_run` 默认 true；`allow_monthly` 默认 false；`max_calls` 硬顶 40（**注意：现有 `HARD_MAX_CALLS=40` 是单次上限，若按 46 次/模型 × 4 模型要跨多次调用**——见 2.4 的执行方式要求）。

### 2.4 执行方式（重要，别一次跑爆）

1. 先 `dry_run:true, suite:'formal'` 预检每个模型（**零调用**），核对题数、预计调用数、排除项。
2. 真实跑：`dry_run:false, suite:'formal', models:['deepseek-flash','deepseek-v4-pro','mimo-v2.6-flash','mimo-v2.6-pro'], max_calls:40` —— 单次最多 40 次，一个模型 46 次会超，所以**按模型分批**多次调用（每个模型一次 `models:[该模型]`，必要时 `max_calls:46`... 若被硬顶截断，就分两次跑同一模型并合并？**不允许合并不同 run 的分数**）。
   实际做法：收紧题量到单模型 ≤40 次 —— **把 orchestration 从 8 题降到 6 题**（合计 44 次/模型），仍超 40。再降：long_context 12→10、coding 12→10、tools 12→10、orchestration 6、哨兵 2 = **38 次/模型**，单次 `max_calls:40` 可完整跑完一个模型。
   → **按此定稿：coding 10 / tools 10 / long_context 10 / orchestration 6 / sentinel 2 = 38 次/模型，四模型共 152 次**。请把 §2.1 的题量表按这一版实现，并在报告 §1 说明「每 graded 维 ≥6、合计 36 题；per-dim n=10/10/10/6」。
3. 每个模型跑完立即把该模型结果落盘（`model_eval`），再跑下一个；中途失败就记录并继续下一个，不要卡死。
4. 全程**不要**写 `model_ratings`；确认 `git diff` 里没有 `cordis.patch.yml` 之外的意外改动。

## 4. 取档公式（必须原样实现并在报告 §3 注明）

对每个 graded 维：`p = passed / n`，`lb = wilsonLowerBound(p, n)`（现有函数，95%）。

| 建议档位 | 条件 |
|---|---|
| `excellent` | `lb ≥ 0.75` 且 `p ≥ 0.92` |
| `good` | `lb ≥ 0.55` |
| `fair` | `p ≥ 0.30`（且不满足 good） |
| `none` | `p < 0.30` |
| `无数据` | 该维 `null`/`skipped`/样本不足（n < 6） |

`vision` 恒 `无数据`（宿主 llm 把图投影成文本占位，M5-MVP 已实证）；`world_knowledge` 只作哨兵，报告里单列「校准结果」并说明**不计入 composite、不建议档位**。

综合建议（表末列）用一句话给出：优先看 `coding / tools / long_context` 三维里最低的那档，并标注「是否足以支撑 priority_delta」。

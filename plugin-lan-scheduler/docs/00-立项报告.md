# 00 · 立项报告：LAN 薄任务调度层（dsh-lan-scheduler）

- 日期：2026-11-20（P2-P5 正确性深化后修订）
- 状态：0.1.1 正确性深化完成，四节点实测通过；P6 独立审计 PASS-WITH-FINDINGS，major 已修/降级文档声明
- 关联：`docs/briefs/lan-dsh-interconnect-test.md`、`docs/briefs/dsh-mesh-capability-assessment.md`

## 1. 背景

四台 DSH（.23 两个实例、.21 一个、.24 一个）已用 `dsh-interconnect@0.17.0` 打通双向会话消息。  
但“能发消息”不等于“有任务”：

- 没有任务台账：派了什么、谁在做、做到哪，全靠会话上下文。
- 没有失败语义：对端不在线/会话被回收时，消息要么丢，要么人工重发。
- 没有并发控制：一个 worker 同时接多单，容易串话。
- 没有审计：结果散落在多个会话里，无法汇总。

`dsh-mesh@0.3.50` 评估结论是：有文件分块与点对点 `delegate`，但无队列/优先级/cron/DAG/重试/租约，补不上调度层。  
因此本项目做一个**薄层**：只补任务台账、派发、重试、租约、回执，不重造通讯。

## 2. 目标

1. 协调者 DSH 上一个插件，暴露 9 个 `sched_*` 工具。
2. 台账持久化为单个 JSON 文件，重启不丢。
3. 投递复用 `ctx.interconnect.send()`，不新增端口/协议。
4. 支持 queued 排序、租约超时回收、线性退避重试（30s×attempt，封顶 5min）、取消。
5. worker 用 `interconnect_reply` 回纯 JSON，协调者 `sched_ingest` 落账。
6. 四台 DSH 各派一单，全部 succeeded。

## 3. 非目标

- DAG、依赖图、抢占、优先级反转。
- 强杀对端已开始的模型回合（`sched_cancel` 只改台账，不杀进程）。
- 跨机文件传输（worker 用 `files` 回报路径；传输另走 dsh-mesh/共享盘）。
- 多协调者共享台账（单写者）。
- 替代 `dsh-interconnect`（它是前提，不 fork）。

## 4. 架构

```text
coordinator DSH (dsh-a)
  └─ @local/dsh-lan-scheduler
       ├─ sched_* tools  ← agent
       ├─ LanScheduler   ← state.json (single writer)
       └─ ctx.interconnect.send({ instanceId, sessionId, text, sender })
                              │  followup + resume
                              ▼
worker DSH (dsh-b/c/d)
  └─ worker session
       ├─ executes task (tools)
       └─ interconnect_reply({ text: JSON })
                              │
                              ▼
coordinator: sched_ingest(text) → task.result
```

关键决定：

- **不用 WebSocket 服务器**：`interconnect` 已有 link/重连/鉴权，调度器只做业务层。
- **不读 worker 的 Web API**：协调者不持有对端 launch token；只靠消息。
- **append-only journal + 派生快照**：每次变更先追加 `.journal.jsonl`（fsync + sha256 链）再应用；`state.json` 是派生缓存，损坏时从 journal 重放。mid-file 坏行拒绝加载并备份为 `.corrupt-*`，只自动截断末尾无换行 tail。
- **worker 由人/agent 登记**：必须是在线会话；调度器不自动创建会话（避免远程创建会话的权限与生命周期问题）。

## 5. 状态机

```text
submit ──> queued ──dispatch──> dispatching ──ack──> running ──ingest──> succeeded
              ▲                    │                  │
              └── retry/backoff ───┘                  ├── lease expired ──> queued
                                                     └── cancel ─────────> cancelled
                                                              failure ────> failed
```

- `dispatching` 是“已调用 send、等 worker 回执”的短窗口；send 返回 delivered 后进入 `running`。
- `running` 有租约（默认 30 min）；过期且无回执 → 回 `queued`，`attempts+1`。
- `attempts >= maxAttempts`（默认 3）→ `failed`。
- 退避：`30s * attempts`，封顶 5 min（线性，不是指数）。
- `sched_tick` 手动触发回收/重试/派发；没有后台定时器（0.1.1 由 agent 或外部 cron 调）。

## 6. 工具契约

| 工具 | 关键参数 | 返回 |
|---|---|---|
| `sched_worker_register` | `instanceId, sessionId, label?, maxConcurrent?` | `{ok, worker}`；同 instance+session 幂等 |
| `sched_worker_list` | — | `{workers, stats}` |
| `sched_submit` | `title, prompt, targetInstanceId?, targetWorkerId?, priority?, dedupeKey?` | `{ok, task}` |
| `sched_status` | `taskId` | `{ok, task}` |
| `sched_list` | `limit?, status?` | `{ok, tasks, stats}` |
| `sched_ingest` | `text`（纯 JSON 字符串）、`attempt`、`lease_token` | `{ok, task, ingested}`；拒绝 `invalid-status`/`stale-lease`/`attempt-mismatch` |
| `sched_tick` | — | `{ok, recovered, retried, dispatched}` |
| `sched_cancel` | `taskId` | `{ok, task}` |
| `sched_stats` | — | `{ok, stats, stateFile, journalFile}` |

worker 回执格式：

```json
{"task_id":"t-...","attempt":1,"lease_token":"lt-...","status":"succeeded","summary":"...","files":[],"error":null}
```

`status` 可为 `succeeded|success|failed`；`sched_ingest` 按 `task_id` 找任务，未知 id 返回 `task-not-found` 但不抛。

## 7. 安全

- 调度器不接触 token/key；只调用 `ctx.interconnect`，鉴权由 interconnect 的共享 token 负责。
- worker 必须是协调者已配置 peer 的活会话；`send` 的 `session-owned-by-subagent` / `resume-refused` 会作为失败原因回写。
- 台账含任务 prompt 与结果，可能含敏感内容；Linux 上 `state.json`/journal 以 600 创建，Windows 上 `0o600` 不生效，需用 ACL 限制到运行用户；勿入仓库。
- 当前 LAN 为明文 HTTP/WS，仅可信网段；需要更强隔离时在 interconnect 层加 SSH 隧道/TLS，不改调度器。

## 9. 风险与后续

- 无通用 AsyncMutex：靠 JS 单线程同步段 + `tick` 单飞 + `inFlight` + send 后重读；跨进程多协调者不在当前范围。
- 租约用墙钟 `Date.now()`：NTP 回拨/前跳会影响租约；后续可改单调时钟（跨重启仍要持久化基准）。
- journal/任务数量无上限：需监控或后续加轮转；`state.json` 里保留失败任务/旧 worker，后续加 `sched_prune`。
- 无后台定时器：依赖 `sched_tick`；后续可加 host timer（`ctx.setInterval`）但需确认宿主生命周期。
- worker 需要 standing rule：新 worker 第一次接单前要教它回执协议；后续可在 task prompt 里自动附协议说明。
- 真实故障矩阵未做全：只做了 dsh-d 进程被杀重派（无 raw 归档）；真实断电/网络分区/时钟漂移/pcap 仍属计划中。
- 多协调者/高可用不在当前范围。

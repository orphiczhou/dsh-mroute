# 00 · dsh-lan-trust 立项与安全边界

## 1. 问题

四台 LAN 节点都是 DSH CLI `dsh web`（headless web），每个实例启动时打印一次性 URL：

```text
dsh web: http://192.168.3.23:3081/?token=<launch-token>
```

直接打开 `http://192.168.3.23:3081/` 返回 401：

```text
dsh web authentication required; reopen the URL printed by dsh web.
```

用户要求“WEB 界面打开不需要 token，局域网内信任”。目标不是关闭 DSH 认证，而是提供一个**可信 LAN 的自动登录入口**：用户在 LAN 内打开固定地址即可进入，不再手工粘贴/传递 token。

## 2. 不能直接关掉认证

源码核验（DSH 0.2.2-rc.3）：

- `dsh-client-connection/src/browser-auth.ts` 每个进程生成随机 launch token；`authorizeIndex()` 只认 `?token=` 或签名 cookie，否则 401。
- `rpc-host.ts` 的 `HostConnectionService.admit()` 先做 Host/Origin fence，再要求 `browserAuth.isAuthenticated()`；`trustedHosts` 只影响前者。
- `index.ts` 的 Connection Config 只有 `recovery` / `trustedHosts` / `cookieMaxAgeDays` / `maxRequestBodyBytes`，没有 `noAuth` / `trustedNetworks`。
- 运行时路由使用的是 app-boot 打包进 `dsh-client-connection/lib/index.js` 的副本，插件动态 import 到的 `HostConnectionService` 不是同一份；替换类原型无效（实测补丁执行但 401 不变）。

结论：不改内核/打包层，新增入口网关。

## 3. 方案

`dsh-lan-trust` 与 DSH 同进程运行：

1. 模块/`apply` 早期 tee `process.stdout.write`，从启动行捕获 `?token=...`，只存内存。
2. `node:http` 网关监听 `0.0.0.0:<port>`（默认 3095）；只接受 `allowedCidrs` 内的**直接 socket**源。
3. 浏览器 `GET /` → 网关服务端 `fetch(origin + '/?token=<captured>', redirect:'manual')`。
4. DSH 返回 `Set-Cookie: dsh-auth-...`（HttpOnly、SameSite=Strict、30 天）；网关原样回给浏览器，302 到 `origin/`。
5. 之后浏览器带 cookie 访问 DSH 3081，正常进入工作区。

token 不出现在浏览器 URL、HTML、JS、面板配置或网关日志中。

## 4. 目标 / 非目标

**目标**

- 可信 LAN 内固定入口免 token 打开四台 DSH Web。
- 不改 DSH 监听端口、不改 DSH 认证、不把 token 写盘。
- 非 allowlist 源明确 403。
- 面板“打开界面”直接指向网关。

**非目标**

- 不做公网暴露、不做反代、不做 OAuth/SSO。
- 不做面板级认证（网关本身无认证）。
- 不把 DSH 3081 变成匿名入口。
- 不做多用户/角色隔离：allowlist 内即 owner。

## 5. 安全模型（必须接受才部署）

- **信任边界 = `allowedCidrs`**：默认 `192.168.3.0/24` + loopback。该网段内任意主机访问网关即获得 owner 权限。
- 只认 `req.socket.remoteAddress`；不解析 `X-Forwarded-For`。放在反代后会把所有请求看成反代地址，**禁止**。
- token 仅内存；但 DSH 自己的启动日志仍可能含 token，必须 600/ACL。
- 网关无认证、无限流；LAN 被入侵时攻击者可拿到 owner。需要更强隔离时用 WireGuard/Tailscale ACL 或面板认证后再开。
- 不能暴露到公网；不能把 3095/3096 映射到路由器。

## 6. 部署

| 节点 | DSH | 网关 |
|---|---|---|
| dsh-a | `.23:3081` | `.23:3095` |
| dsh-b | `.23:3082` | `.23:3096` |
| dsh-c | `.21:3081` | `.21:3095` |
| dsh-d | `.24:3081` | `.24:3095` |

bundle patch 提供 port 3095/CIDR；每节点 profile `cordis.patch.yml` 补 `origin`（A/B 用 3081/3082，端口 3095/3096）。Windows 防火墙放行 3095。

## 7. 验收

- `GET /health` → `{ok:true, tokenCaptured:true}`。
- `GET /` → 302 + `location: origin/` + `set-cookie: dsh-auth-...`。
- 带 cookie 请求 DSH `origin/` → 200。
- 无 token 浏览器打开网关 → 最终 `http://<lan>:3081/`，标题 `DeepSeek Harness`，无 “authentication required”。
- 非 allowlist 源 → 403（CIDR 单测覆盖；本机无第二网段，端到端待补）。
- 面板四节点“打开界面”指向 3095/3096，不再出现 token 输入框。

## 8. 已知限制

- token 捕获依赖启动行格式；DSH 升级改日志格式会失效，需重新验证 `tokenCaptured`。
- 网关只适用于直连 LAN；反代/XFF 不支持。
- cookie 30 天；换 token/重启后旧 cookie 仍有效直到过期（DSH 行为）。
- 没有速率限制/审计日志；需要时在 LAN 防火墙/交换机层做。
- 本机无法模拟第二网段，非信任源拒绝目前只有单元测试，没有端到端证据。
